# 01-selection · 同一个需求，三种写法

第 1 章的配套示例。不是一个"AI 应用"，而是一次**对照实验**：同一份假上游、同一个问题，只换写法，看差别出在哪。

## 演示什么

三种写法，都能跑，都能出结果：

| 写法 | 类 | 有效行数 | 拿得到 token | 上游挂了能活吗 |
| --- | --- | --- | --- | --- |
| A 裸 HTTP | `RawChat` | 16 | ❌ | ❌ |
| B 自己封一层（接口 + 降级） | `LayeredChat` + `Chat` | 18 + 8 | ✅ | ✅ |
| C 托管网关（黑盒） | `GatewayChat` | 10 | ❌ | ❌ |

**关键不是行数，是那 10 行的位置。** B 比 A 多 10 行，多出来的两个缝：接口（可替换）、主备（可降级）。

## 怎么跑

```bash
cd examples/01-selection
mvn spring-boot:run
```

```bash
# 三种写法各跑一遍：先正常，再把上游切成故障
curl -s localhost:8080/api/compare | jq

# 数行数（直接从源码文件数，不是估的）
curl -s localhost:8080/api/loc | jq

# 单独调一种，看返回结构差在哪
curl -s 'localhost:8080/api/ask?q=退款多久到账&impl=raw' | jq
```

> 不联网、不要 key。假上游是进程内的，所以三种写法的差异**只来自代码形状**，不来自模型。

## 预期看到什么

### `/api/compare`

```
正常:
  raw      存活 ✓  耗时 69ms  拿得到token ✗
  layered  存活 ✓  耗时 60ms  拿得到token ✓  能看出provider ✓
  gateway  存活 ✓  耗时 62ms  拿得到token ✗

上游故障:
  raw      存活 ✗  "上游 503：模型服务暂时不可用"
  layered  存活 ✓  耗时 62ms  （已降级到 backup）
  gateway  存活 ✗  "上游 503：模型服务暂时不可用"
```

**三行耗时几乎一样** —— 这是有意的：抽象层不是性能问题。差异全在「故障时能不能活」和「拿不拿得到计量信息」。

### `/api/loc`

```
RawChat.java       16
LayeredChat.java   18
GatewayChat.java   10
Chat.java           8
```

## 已经验证过的

| 项 | 结果 |
| --- | --- |
| 三种写法正常路径 | 全部存活，文本完全一致（同一份假上游） |
| 上游故障 | raw 抛异常、gateway 抛异常、**layered 存活**（降级） |
| 计量信息 | 只有 layered 能拿到 `promptTokens` / `provider` |
| 行数 | 16 / 26 / 10，与 `/api/loc` 输出一致 |
| 耗时 | 60–69ms 三档接近，说明抽象不带来额外延迟 |

## 别被这个示例误导的地方

- **假上游是假的**：它不验证 prompt 质量，只验证代码形状。真实模型的差异在别的地方。
- **C 不是"坏方案"**：短期项目、个人验证、不想维护接入层，用托管网关完全合理 —— 只要你清楚自己放弃了什么。
- **行数不是唯一指标**：B 多 10 行，但如果你这个功能只活两周，这 10 行可能是负收益。第 1 章的取舍表讲的就是这个。
