# 第 6 章 · 熔断与限流：Redis + Lua 令牌桶

## 这一章解决什么问题

两个方向都会出事。

**打出去太猛**：你的服务在促销那天给模型发了 3000 个请求，厂商套餐的 RPM 是 600，直接把你封了一分钟。这一分钟里所有用户都失败 —— 而你已经付过钱了。

**打进来太猛**：高峰期请求堆在 Tomcat 线程池里，每个都在等上游 30 秒超时。线程池满了，健康检查也返回不了，K8s 把你的 Pod 干掉，流量打到剩下的 Pod，它们也满了 —— 雪崩。

上一章讲了"主路挂了换谁"，但没讲"怎么别再打它"。你已经知道主路挂了，代码还在每秒打它两百次，每次等 900ms。

这一章补上这两块：**令牌桶管住出去的速率，熔断器管住不再打坏掉的目标。**

## 你会得到

- 一个原子、精确的令牌桶 —— 并且亲眼看到不原子会超发多少（实测：容量 10，放过去 40 个）
- 一份 Redis + Lua 的完整脚本，以及为什么这几行必须放在脚本里
- 一个三态熔断器，带实测的状态转换时间线
- 一组可以直接抄的参数起点：capacity、refill、失败阈值、冷却时长

## 6.1 熔断不是限流

这两个词也经常混着用，但它们的触发条件完全不同：

| | 限流 | 熔断 |
| --- | --- | --- |
| 触发条件 | 你**主动**设的阈值（QPS / RPM / TPM） | 对方**实际**的表现（失败率 / 连续失败） |
| 保护的是谁 | 厂商的配额、你自己的下游 | 你自己的线程池、你的用户的等待时间 |
| 正常时会触发吗 | 会，流量高峰就触发 | 不会，一切正常时它是透明的 |
| 拒绝时用户看到 | 429 稍后再试 | 立刻失败或走降级 |

一句话区分：**限流是"我最多只能吃这么多"，熔断是"这道菜坏了，别吃了"。**

两者都要有，因为缺一个都会出事：

- 只有限流：主路挂了，你依然按 600 RPM 匀速打过去，每次等 900ms，线程池照样被占满
- 只有熔断：主路好好的，但你没控制速率，把厂商的配额打爆，被封号

## 6.2 从 RPM 到两个数字

令牌桶只有两个参数，但大部分人是拍脑袋填的。正确做法是从厂商的配额反推。

设厂商给的 RPM 是 600：

```
平均速率 = 600 / 60 = 10 QPS   →  refillPerSec = 10
```

那 `capacity` 给多少？**看你需要容忍多大的突发。**

真实业务从不匀速：可能 10 秒没请求，然后一秒来 40 个。如果你把桶做得刚好（capacity=10），那 40 个请求里 30 个会被拒 —— 明明这一分钟的总量才 40 个，远低于 600。

所以：

```
capacity = refillPerSec × 容忍的突发秒数
```

2–4 秒是比较安全的起点：`capacity = 10 × 3 = 30`。

### 为什么不用固定窗口

固定窗口的实现最省事，`INCR` + `EXPIRE` 就完了。但它在窗口边界上会放进来两倍的量：

```
限流：100 次/分钟，固定窗口
12:00:59  ← 打了 100 次（这一分钟的第 100 次）
12:01:00  ← 又打了 100 次（新一分钟的第 1 次）
──────── 实际效果：2 秒内 200 次 ────────
```

厂商看到的不是"每分钟 100 次"，而是"2 秒 200 次"，照样封你。

令牌桶没有这个问题：令牌是连续补充的，2 秒最多补充 `2 × refill` 个，物理上就不可能出现瞬间双倍。

### 为什么不用漏桶

漏桶是固定速率流出，**不允许突发** —— 来了 40 个请求，它按每秒 10 个慢慢处理，剩下的排队。

对 LLM 调用这是灾难：排队让 p99 延迟直接翻几倍，而用户等的是首字，不是排队。

**令牌桶允许在容量内瞬间打完，长期平均又不超** —— 这正是聊天场景需要的形状：用户偶尔连点几下能立刻响应，但不能天天连点。

## 6.3 为什么必须原子：一次实测

令牌桶的逻辑只有三步：

```java
double tokens = bucket.tokens + 补充的令牌;   // ① 读
if (tokens < cost) return false;              // ② 判断
bucket.tokens = tokens - cost;                // ③ 写
```

三步分开写，并发下就会超发。**不是"可能"，是必然** —— 窗口 = ① 和 ③ 之间的时间，40 个线程同时进来，就有一堆线程读到同一个旧值。

示例里专门留了一个故意写错的版本（`NaiveTokenBucket`），还人为在这个窗口里加了 0.2ms 让并发容易撞上。实测：容量 10，40 个请求同时打进来 ——

```json
{"impl":"naive","capacity":10,"concurrent":40,"passed":40,"rejected":0,"oversold":30}
```

**40 个全过去了。** 你的限流器形同虚设，而且还给了一种"我已经限流了"的错觉 —— 这种错觉比没有限流更危险。

把 ①②③ 放进同一个临界区之后：

```json
{"impl":"atomic","capacity":10,"concurrent":40,"passed":10,"rejected":30,"oversold":0}
```

**10 个通过，30 个被拒，一个不多。** 同一次压测，同样的并发，只差一次加锁：

```java
synchronized boolean tryTake(long now, double refillPerSec, int cost) {
    double filled = Math.min(capacity, tokens + (now - lastRefillNanos) / 1e9 * refillPerSec);
    tokens = filled;
    lastRefillNanos = now;

    if (filled < cost) return false;
    tokens = filled - cost;
    return true;
}
```

> 这里有个我自己的翻车记录，值得单独说：第一版我写的是"判断在锁外、只给写入加锁"的伪 CAS。同样的 40 并发，通过数是 **11** 个 —— 超发 1 个。
>
> 少这一个的原因很微妙：两个线程都在锁外读到了 `tokens=10`，只有一个抢到写，另一个也成功写入（因为它只加了锁、没做比较）。**只锁一半，等于没锁；而且这种 bug 只超发一个，压测不仔细根本看不出来。**

### 进程内的锁解决不了多实例

`synchronized` 只在一个 JVM 里有效。你部署三台，每台一份桶，等于把限额放大了三倍 —— 而厂商看到的是三倍流量。

多实例只有一个答案：**把桶放到所有实例都能看见的地方，并且在那里原子地完成三步。** 这就是 Redis + Lua。

## 6.4 Redis + Lua

Redis 是单线程执行命令的，一个 Lua 脚本在执行期间不会被其他命令打断 —— 于是"三步"在这个脚本里天然是原子的。

```lua
local key      = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill   = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local cost     = tonumber(ARGV[4])

local data   = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])

if tokens == nil then
  tokens = capacity
  ts = now
end

local delta = math.max(0, now - ts) / 1000.0
tokens = math.min(capacity, tokens + delta * refill)

local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end

redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(capacity / refill * 1000) + 60000)

return allowed
```

实测（同样容量 10、40 并发）：

```json
{"impl":"redis","capacity":10,"concurrent":40,"passed":10,"rejected":30,
 "oversold":0,"elapsedMs":110}
```

10 个通过，一个不多。代价是 110ms —— 进程内版本是 9ms。**这就是分布式限流的成本：每个请求多一次 Redis 往返。**

### 三个容易踩的坑

**坑一：时间戳由谁传**

脚本里不能调 `redis.call('TIME')` —— 或者说不该调。`TIME` 返回的是 Redis 服务器的时间，而在 Redis Cluster 里，脚本是可以在从节点执行的，主从的时间可能有偏差。更重要的是：**如果脚本自己取时间，你就没法测试「令牌应该补多少」这件事。**

所以 `now` 由调用方传入（`System.currentTimeMillis()`）。代价是各应用服务器之间的时钟偏差会影响补充计算 —— NTP 校时精度在毫秒级，对限流来说完全够用。

**坑二：拒绝时也要写回**

看脚本第 27 行：**不管 allowed 是 0 还是 1，都要 `HMSET` 写回**。

如果你只在通过时写回，那么被拒的请求不会推进 `ts`，下次调用时算出的 `delta` 会把这段已经被算过的时间再补一次 —— 令牌凭空多出来。这种 bug 只在"持续打满"的时候出现，平时测不出来。

**坑三：TTL 不能太短**

`PEXPIRE` 的时间必须大于「桶从空到满」的时长（`capacity / refill` 秒），否则桶会在还没补充完的时候被删掉，下次调用重新以满桶开始 —— 又白送一波突发。

脚本里给的是 `capacity / refill × 1000 + 60000`，多留 60 秒。

### Java 侧只有几行

```java
boolean tryAcquire(String key, int cost) {
    Long allowed = redis.execute(
        script,                                  // DefaultRedisScript，指向 bucket.lua
        List.of("rl:" + key),                    // KEYS
        String.valueOf(capacity),                // ARGV[1]
        String.valueOf(refillPerSec),            // ARGV[2]
        String.valueOf(System.currentTimeMillis()), // ARGV[3]
        String.valueOf(cost)                     // ARGV[4]
    );
    return allowed != null && allowed == 1L;
}
```

`redis.execute(script, keys, args...)` 会把脚本一次性发过去（Spring 会自动用 `EVALSHA` 缓存），**不要自己拼字符串** —— 参数注入是小事，拼错了 `KEYS` 和 `ARGV` 的顺序是大事。

## 6.5 被限流了怎么回给调用方

三种处理方式，选错了会放大故障。

**方案一：阻塞等待（不推荐）**

拿不到令牌就 `Thread.sleep` 等到有。看着很优雅，实际上把请求堆在你的线程池里 —— 高峰期等着等着，线程池就满了，然后连健康检查都返回不了。

**方案二：快速失败 + 429（推荐）**

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
```

关键是**算准 `Retry-After`**，不要写死：

```
Retry-After = 需要的令牌数 / refillPerSec  （向上取整）
```

要 1 个令牌、每秒补 5 个 → 1 秒。要 10 个 → 2 秒。调用方照着这个时间重试，成功率会高很多；写死 1 秒的话，需要 10 个令牌的请求会连续撞好几次。

**方案三：降级到备路（看情况）**

对**按租户的配额**限流，不该降级 —— 他额度用完了就是完了。
对**按厂商的 RPM** 限流，可以降级 —— 换一家还有配额，这正是第 5 章那条链的用武之地。

同一句"被限流了"，两种来源，两种处理。

## 6.6 熔断器：闭、开、半开

限流管"打多快"，熔断管"还打不打"。

三个状态，两条边：

```
       失败数 ≥ 阈值                    冷却时间到
CLOSED ────────────────→ OPEN ──────────────────→ HALF_OPEN
   ↑                       │                          │
   │                       │ 拒绝所有请求              │ 放一个探测
   │                       │ （不打上游）              │
   └───────────────────────┴──────────────────────────┘
        探测成功                       探测失败 → 回 OPEN
```

示例里的实现（`CircuitBreaker`），核心就这几个方法：

```java
public synchronized boolean tryAcquire() {
    if (state == OPEN) {
        if (System.currentTimeMillis() - openedAtMillis < openMillis) {
            return false;                       // 冷却期内，直接拒绝，不打上游
        }
        state = HALF_OPEN;
        probeInFlight = true;
        return true;                            // 放一个探测请求
    }
    if (state == HALF_OPEN) {
        return false;                           // 半开只放一个，其他的继续拒
    }
    return true;
}
```

`HALF_OPEN` 只放一个探测，这一条特别重要：如果冷却结束就把所有请求放过去，那上游刚恢复（或者还没恢复）就又被一波流量打垮，你会陷入"开 → 半开 → 开"的循环。

### 实测的时间线

跑一遍 `/api/cb/selftest`，阈值 5 次、冷却 800ms：

```
CLOSED  → 失败 1,2,3,4    （每次都真的打到上游）
        → 失败 5          ← CLOSED → OPEN
OPEN    → 连续 8 次拒绝   （单次 ~1µs，上游调用 0 次）
        → 冷却 800ms 结束  ← OPEN → HALF_OPEN，放一个探测
HALF_OPEN → 探测失败       ← 回到 OPEN
        → 再等 800ms       ← OPEN → HALF_OPEN
HALF_OPEN → 探测成功       ← HALF_OPEN → CLOSED
```

关键数字：

| 指标 | 值 |
| --- | --- |
| 熔断期间上游被调用次数 | **0** |
| 熔断期间单次拒绝耗时 | **~1µs** |
| 全程上游被调用总次数 | 7（5 次失败 + 2 次探测） |
| 熔断期 vs 超时 | 1µs vs 900ms，**快 90 万倍** |

最后一行是熔断的全部价值：**它不是让请求成功，是让失败的请求快速失败。**

主路挂掉时，第 5 章那条降级链每次还要先等 900ms 超时才知道"主路真的挂了"。有熔断器的话，这 900ms 直接省掉 —— 用户感知到的切换时间从 900ms 降到 1µs。

### 阈值怎么定

三个参数，起点建议：

| 参数 | 起点 | 理由 |
| --- | --- | --- |
| 失败阈值（连续） | 5 | 太低会被偶发抖动误伤，太高要等太久才熔断 |
| 冷却时长 | 30s（生产）/ 800ms（演示） | 太短会反复试探打垮上游，太长会让恢复变慢 |
| 半开探测数 | 1 | 多个探测等于提前放开流量 |

生产上 30 秒起步：上游那种级别的故障，30 秒内不会自己好。而太短的冷却（比如 1 秒）会让你每秒都去试一次，对已经挂掉的服务来说是持续的额外压力。

## 6.7 熔断和降级怎么配合

上一章那条链，加上熔断之后变成这样：

```
请求 → 熔断器（主路）─放行→ 真的调用主路
              │
              └─拒绝（熔断中）→ 跳过主路，直接走备路
```

**顺序是：先问熔断器，再决定打不打。** 这一句话就能把切换成本从 900ms 降到 1µs。

三件事要注意：

**一、熔断的粒度要跟降级链对齐**

一个 provider 一个熔断器。如果你按"模型名"熔断，那 qwen-plus 挂了、qwen-turbo 还好着的时候，你会把整个 qwen 都停掉 —— 降级链里的第三跳就白排了。

**二、备路也要有自己的熔断器**

主路挂了走备路，备路挂了走第三跳。**每条路都是独立的熔断器**，否则会出现"备路已经在熔断了，你还在往那儿打"。

**三、熔断状态是每实例一份，不是全局的**

三台机器各自的熔断器独立计数：A 认为主路挂了，B 可能还在正常调用。这通常是好事（避免误判扩大），但也意味着**流量不均** —— 可以对熔断事件打点，让监控看到"三台里两台已熔断"。

真要做全局熔断，就得把计数器放到 Redis 里，代价是每个请求多一次往返 —— 而熔断的全部意义就是快。**绝大多数场景不值得。**

## 6.8 结论

如果只记三句话：

1. **限流的三个动作必须在同一个原子操作里。** 判断在锁外、只给写加锁，等于没锁 —— 实测超发 1 个；完全不锁，40 个请求全过。多实例只有 Redis + Lua 一条路。
2. **参数从配额反推，别拍脑袋。** `refillPerSec = RPM / 60`，`capacity = refillPerSec × 2~4`。固定窗口在边界会放进来双倍，漏桶不允许突发 —— 聊天场景只有令牌桶合适。
3. **熔断的价值是"快速失败"，不是"让请求成功"。** 1µs 拒绝 vs 900ms 超时，这是它存在的全部理由；熔断器要和降级链的每一跳一一对应。

可以直接抄的起点：

```yaml
limiter:
  capacity: 30          # refillPerSec × 3，允许 3 秒的突发
  refill-per-sec: 10    # 厂商 RPM 600 / 60
  failure-threshold: 5  # 连续 5 次失败即熔断
  open-millis: 30000    # 冷却 30 秒再探测
```

到这里，"接入层"最硬的三块 —— 统一接入、额度控制、故障隔离 —— 就齐了。下一章换个方向：**一次调用变成一条流水线**之后，怎么让它断在哪一步都能接着跑。
