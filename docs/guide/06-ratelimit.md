# 第 6 章 · 熔断与限流：Redis + Lua 令牌桶

## 这一章解决什么问题

两个方向都会出事：**打出去**的请求超过厂商套餐上限，直接被封一分钟；**打进来**的请求在高峰期把服务线程池占满，整个系统一起卡死。

## 你会得到

- 一个原子、精确、能扛住并发的令牌桶限流器（不是 `if (count++ < 100)` 那种）
- 一个带半开状态的熔断器，避免「挂了才切、切了又试、试了又挂」
- 对厂商 RPM / TPM 上限的正确应对姿势 —— 在客户端限流，不要等它返回 429

## 提纲

- **6.1 为什么是令牌桶** —— 固定窗口的临界问题、漏桶的突发不友好，各自用一个例子讲清
- **6.2 为什么必须用 Lua** —— 三步操作之间的竞态，以及一次真实的超额事故
- **6.3 令牌桶的 Lua 实现** —— 完整脚本 + 时间戳由谁传入（这里有个坑）
- **6.4 Java 侧封装** —— 阻塞还是快速失败？返回什么给调用方？
- **6.5 熔断器状态机** —— 闭、开、半开，三个状态之间的转换条件
- **6.6 熔断和降级的配合** —— 先熔断，还是先降级？
- **6.7 限流维度设计** —— 全局 / 按密钥 / 按模型 / 按业务线，多层怎么叠加
- **6.8 结论** —— 一组可直接抄的参数起点
