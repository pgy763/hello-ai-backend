# 第 11 章 · 压测与容量规划

## 这一章解决什么问题

上线前你不知道能扛多少，上线后你不知道为什么慢。

更麻烦的是：**AI 接口的容量问题和普通接口完全不同。** 你按老办法压了一遍，TPS 卡在 20 上不去，于是加机器、加线程、换框架 —— 一点用都没有。因为瓶颈不在你的机器上。

这一章把这件事讲清楚，并且给你两个能直接用的东西：**一条压测方法**，和**一张能改数字就用的容量表**。

## 你会得到

- 一张实测的饱和曲线：并发从 1 加到 64，吞吐怎么变、延迟怎么变
- 一条公式解释为什么「加线程没用」（利特尔法则，附自检方法）
- 一个坑：限流返回 500 而不是 429 会发生什么
- 正向估算（DAU → 并发 → 线程 → 套餐 → 成本）和反向估算（上游配额 → 能扛多少 QPS）

## 11.1 为什么普通压测方法失效

普通 Web 接口的压测是这样：调大并发，看 TPS 涨到哪、什么时候开始报错。经验值是「单机几百到几千 TPS」。

拿这套方法压 LLM 接口，会得到三个看不懂的结果：

| 现象 | 你的第一反应 | 真实原因 |
| --- | --- | --- |
| TPS 卡在个位数，怎么加线程都不涨 | 我的服务有性能问题 | 上游只给你这么点并发，你在排队 |
| P99 是 P50 的 8 倍 | 有慢查询/锁竞争 | 排队长度不同，队尾自然慢 |
| 压测账单比预期高十倍 | 计费错了 | 压的是真模型，每个请求都在烧钱 |

根源在三个差异上：

**一、单请求耗时差两个数量级。** 普通接口 50ms，LLM 接口 2500ms —— 差 50 倍。这直接决定了下一条。

**二、瓶颈在上游。** 你的 Tomcat 能开 200 个线程，但厂商那边给你的并发可能是 50。你开 200 个线程，只是让 150 个在排队。

**三、成本按 token 计，且不可预测。** 压 10 万次普通接口，成本是电费；压 10 万次真实 LLM 接口，成本是几千块 —— 而且输入长度不同，成本还不同。

所以压测要分两步走：**先用假上游把自己的接入层压穿，再用真上游验证一次真实链路。**

## 11.2 该压什么：四个指标和一条公式

不要只看 TPS。四个指标一起看：

| 指标 | 含义 | 看什么 |
| --- | --- | --- |
| **吞吐（RPS）** | 每秒完成多少请求 | 饱和点在哪 |
| **P95 / P99 延迟** | 95%/99% 的用户等了多久 | 用户体感 |
| **失败率** | 500 / 429 / 超时 各占多少 | 是不是在硬扛 |
| **在飞请求数** | 同时有多少个没返回 | 真正的并发需求 |

最后一个最容易被忽略，但它是**唯一能直接换算成线程数**的指标。

### 一条公式：利特尔法则

```
并发数 = QPS × 单请求耗时
```

这条公式（Little's Law）不是经验值，是排队论的恒等式。它解释了你遇到的一切：

| 场景 | QPS | 单请求耗时 | 需要的并发 |
| --- | --- | --- | --- |
| 普通查询接口 | 100 | 50ms | **5** |
| LLM 接口（同 QPS） | 100 | 2500ms | **250** |

**同样是 100 QPS，LLM 接口需要 50 倍的并发。** 这就是为什么「加线程」在普通接口上从来不是问题，在 LLM 接口上却是核心问题。

反过来说：**上游给你 50 个并发，你能扛的 QPS 就只有 50 ÷ 2.5 = 20。** 想再多，只能降延迟（换更快的模型）或者加配额（花钱）。

## 11.3 实测：把上游剥离，先压自己的接入层

示例模块 `11-capacity` 用一个假上游代替真模型：**8 个槽位、每个请求占 400ms**。这就是真实厂商的行为 —— 并发能力由它定，不由你定。

压测器是自压（HTTP 打自己），四组参数全可调。

```bash
# 上游：8 个并发槽位，每次 400ms，RPM 不限
curl -s -X POST 'localhost:8080/api/config?slots=8&latencyMs=400&rpm=100000'

# 压测：并发 16、每线程 8 次
curl -s -X POST 'localhost:8080/api/load?concurrency=16&perWorker=8' | jq
```

实测饱和曲线（上游 8 槽位 / 400ms）：

| 客户端并发 | 吞吐 RPS | P50 | P95 | 平均延迟 | 在飞请求数 |
| --- | --- | --- | --- | --- | --- |
| 1 | 2.40 | 414ms | 450ms | 416ms | 1.0 |
| 2 | 4.85 | 414ms | 419ms | 411ms | 2.0 |
| 4 | 9.72 | 415ms | 417ms | 411ms | 4.0 |
| 8 | **19.47** | 407ms | 417ms | 410ms | 8.0 |
| 16 | 19.82 | 805ms | 815ms | 781ms | 15.5 |
| 32 | 19.77 | 1612ms | 1623ms | 1539ms | 30.4 |
| 64 | 19.78 | **3232ms** | **3248ms** | 3054ms | 60.4 |

这张表值得读三遍。

**并发 ≤ 8（等于上游槽位）：线性增长，延迟不变。**

并发 1 → 2.40 RPS，并发 8 → 19.47 RPS，几乎正比。延迟稳定在 410ms 左右（400ms 上游 + 10ms 开销）。**这段是可以随便加并发的区间。**

**并发 = 8：到达饱和点。**

理论值 8 ÷ 0.4s = 20 RPS，实测 19.47 RPS。**这就是这套配置的天花板。**

**并发 > 8：吞吐一动不动，延迟精确翻倍。**

并发 16 → 19.82 RPS，32 → 19.77，64 → 19.78。吞吐一条直线，延迟 407 → 805 → 1612 → 3232，**每翻一倍并发，延迟就翻一倍**。

这就是排队的本质：上游只有 8 个位置，来了 64 个请求，56 个在门口排着。**你加的不是处理能力，是队伍长度。**

**在飞请求数 ≈ 并发数** —— 最后一列和第一列基本相等，说明利特尔法则成立。这也是压测器自检的一部分：如果这两列对不上，说明压测器自己有问题（比如压测线程池和 HttpClient 共用线程导致自锁）。

> 那个自检不是凑数的。第一版压测器把压测线程池也交给了 `HttpClient`，并发为 1 时压测线程阻塞在 `send()`，而 HttpClient 要线程干活 —— 自锁，一个请求都发不出去。**这类 bug 只在压测时暴露，因为平时的并发是 1。**

## 11.4 饱和之后：两个必须知道的陷阱

### 陷阱一：把限流错当成故障

上游有配额（RPM/TPM）。超了怎么返回，差别巨大。

```java
// 错误：抛普通异常 → Spring 默认返回 500
throw new RuntimeException("超过 RPM");

// 正确：明确 429，并给 Retry-After
return ResponseEntity.status(429).header("Retry-After", "60").body(...);
```

实测（同一并发 16、总 320 次请求，把 RPM 从「不限」改成 100）：

| 配置 | 成功 | 429 | P50 | P95 |
| --- | --- | --- | --- | --- |
| RPM 不限 | 320 | 0 | 216ms | 219ms |
| RPM 卡到 100 | **100** | **220** | **1ms** | 218ms |

第一版我漏了 429 映射，结果是 220 个请求变成 500 —— 压测器把它们记成「失败」，看起来像服务挂了；而如果是调用方看到 500，它会**重试**，越重试越崩。

**这两条线必须分清：**

- `429` = 配额用完，请**等**（有 `Retry-After`）
- `500` = 我方故障，请**重试**（但对 LLM 这种贵操作，重试要慎重，见第 5 章）
- `503` = 上游过载，请**退避**

### 陷阱二：P50 变好看了，但服务更差了

看上面那张表的 P50：**从 216ms 掉到 1ms**。

因为被限流的请求瞬间返回，不占上游槽位。如果你只盯平均延迟或者 P50，会得出「限流之后变快了」的荒谬结论。

**判据必须是「成功率 + P95」一起看。** 单看任何一个指标，都能被优化成谎话。

## 11.5 容量估算：从 DAU 推到套餐

有了公式和饱和点，容量估算就是算术。示例给了一个参数化的计算器：

```bash
curl -s -X POST 'localhost:8080/api/model' | jq
```

默认参数（5 万 DAU、人均 6 次/天、峰值 5 倍、单次 2500ms、输入 1500 / 输出 300 token、示例单价 2 元 / 8 元每百万 token）算出：

| 项 | 结果 |
| --- | --- |
| 日均调用次数 | 300,000 |
| 平均 QPS | 3.47 |
| **峰值 QPS（×5）** | **17.36** |
| **峰值并发数 = QPS × 耗时** | **43.4** |
| Tomcat 线程数（留 50% 余量） | 66 |
| 需要的上游 RPM（含 30% 余量） | 1354 |
| 日 token 量 | 5.4 亿 |
| 日成本 | 1,620 元 |
| 月成本 | 48,600 元 |
| 每用户每月成本 | 0.97 元 |

**四个数字，四个用途：**

- **峰值并发 43.4 → 决定 Tomcat 线程池**。默认 200 够用；但如果你把 `server.tomcat.threads.max` 调小过，这里就是坑
- **RPM 1354 → 决定买什么套餐**。厂商套餐通常按 RPM/TPM 分级，卡这里
- **5.4 亿 token/日 → 用来核对成本**。很多团队只算了调用次数，忘了每轮的上下文会累积（第 2 章）
- **每人每月 0.97 元 → 决定怎么收费**。这个数低于你的定价，项目才成立

### 反向估算：套餐是定死的，算它够不够

更常见的场景是反过来的 —— 配额已经定了，问「能扛多少」。

```bash
curl -s 'localhost:8080/api/model/from-upstream?concurrency=50&latencyMs=2500&targetQps=25' | jq
```

```
上游并发上限      50
单请求耗时        2500ms
理论上限 QPS      20.0
目标 QPS          25
结论              不够，缺口 5.0 QPS
```

**20 QPS 就是这套配置的天花板**，因为 50 ÷ 2.5 = 20。想扛 25 QPS，只有三条路：

1. 加配额（50 → 63 并发）
2. 降延迟（2500ms → 2000ms，等于并发效率提升 25%）
3. 减少调用（缓存、批处理、把简单问题路由给小模型 —— 第 5 章那套路由）

第三条通常最便宜。

## 11.6 压上游要花多少钱

自己的接入层可以用假上游免费压，但真链路必须验一次。预算怎么控：

| 做法 | 成本 | 能验证什么 |
| --- | --- | --- |
| 假上游压接入层 | 0 | 线程池、连接池、超时、限流逻辑 |
| 真上游小流量（100 次） | 几毛钱 | 真实延迟、真实错误码、token 计量准不准 |
| 真上游压满配额 | 几百到几千 | 上限到底在哪（通常**不需要**做） |

**第三行基本可以跳过** —— 厂商的配额是写在合同里的，你压不出来更多。你真正要验的是「配额内我的服务稳不稳」。

一个省钱的做法：**用便宜模型压链路，用贵模型测质量。** 压测只关心延迟和错误率，用最便宜的模型跑；质量评测用小样本 + 好模型（第 9 章那套评测）。

### 价格 × 延迟 × 质量的取舍

这三个永远不可能同时最优。一个实用的决策顺序：

1. **先定延迟上限**（用户能忍多久）。超过 3 秒的等待，大部分 C 端场景就会掉转化
2. **再定质量底线**（能不能接受 10% 的答错）。能自动校验的任务（分类、抽取）底线可以低；面向用户的回答底线要高
3. **最后在满足前两条的模型里挑最便宜的**

反过来（先挑便宜的再看质量）是最常见的错误，因为质量问题的成本是滞后的 —— 等你发现的时候，用户已经走了。

## 11.7 结论

三条结论：

1. **容量问题的核心是并发，不是 QPS。** `并发 = QPS × 耗时`。llm 接口耗时是普通接口的 50 倍，所以同样 QPS 需要 50 倍并发。上游给多少并发，你就只能扛 `并发 ÷ 耗时` 的 QPS。
2. **饱和点之后加线程只会让排队更长。** 实测：并发 8 → 19.47 RPS / P95 417ms；并发 64 → 19.78 RPS / P95 3248ms。**吞吐一点没涨，延迟涨了 7.8 倍。**
3. **压测要先剥离上游。** 用假上游把接入层压穿（免费、可复现），再用真上游小流量验一次真实链路（几毛钱）。别拿真模型压满配额，那是在给厂商送钱。

可以直接改数字用的模板：

```yaml
capacity:
  dau: 50000                  # 日活
  calls-per-user-per-day: 6
  peak-factor: 5              # 峰值 / 平均

  # 这两个数决定一切，务必实测而不是拍脑袋
  avg-latency-ms: 2500        # 从第 8 章的表里取
  upstream-concurrency: 50    # 问厂商要，或者从 429 的 Retry-After 反推

  # 算出来之后反推配置
  tomcat-threads: 66          # = 峰值并发 × 1.5
  rpm-quota: 1354             # = 峰值 QPS × 60 × 1.3
```

**上线前把这张表填一遍，比压测十轮都有用。** 因为大部分容量事故不是「压不出来」，是「根本没算过」。
