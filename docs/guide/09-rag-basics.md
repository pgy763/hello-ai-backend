# 第 9 章 · RAG 落地：向量库选型与切分策略

## 这一章解决什么问题

你想让模型回答"我们的退款政策是什么"，于是把公司文档全丢给它。三种结果，你大概率会遇到第一种或第三种：

1. **答得像模像样，但细节是编的** —— 模型根本没看到那篇文档，它在凭常识猜
2. **答对了** —— 你运气好，文档正好在上下文里
3. **答得驴唇不对马嘴** —— 检索到了错的段落，模型忠实地基于错误信息回答

这三种结果背后是同一个问题：**你没有能力判断"检索到没"和"生成对没"。**

RAG（Retrieval-Augmented Generation）不是一个组件，是三个环节：

```
建索引：文档 → 切分 → 向量化 → 存进向量库
检索：  问题 → 向量化 → 相似度搜索 → 取 top-k 段
生成：  问题 + top-k 段 → 模型 → 答案
```

三个环节里，**前两个是你完全能控制的，也是绝大多数 RAG 效果差的真正原因。** 第 3 步（生成）在今天已经很少出问题 —— 模型足够强，喂对了料就能答对。

这一章把前两个环节讲透，并且给你一个能测的东西：**一个可以量化的评测**，而不是"感觉效果还行"。

## 你会得到

- 三种切分策略的实测对比（召回、成本、命中率），以及为什么"切多大"没有标准答案
- 一套按团队规模选向量库的判据（附一张对照表）
- 换 embedding 模型时会出什么事，以及怎么不重建全量索引
- 一条四步排查路径：检索不准时，先查哪一步
- 一个能直接改成你自有语料的评测框架

## 9.1 问题出在哪一段

先给一个判断方法，比任何"调参指南"都有用：

| 现象 | 大概率是哪一段出了问题 |
| --- | --- |
| 答案完全跑题，像在说别的事 | 检索 —— 拿错了段 |
| 答案框架对、细节错（数字、日期、条件） | 检索 —— 段落相关但缺了关键那一句（常是切分切断的） |
| 答案说"根据资料无法回答"，但资料里明明有 | 检索 —— 没召回到（top-k 太小、或 embedding 语义没匹配上） |
| 检索到的段落完全正确，答案还是错 | 生成 —— prompt 排版/指令问题，或者模型能力不够 |

**先分清是哪一段，再动手。** 大部分团队一上来就换更大的模型，其实问题在切分。

## 9.2 切分：最不花钱，最影响效果

切分是 RAG 里唯一一件"不花钱、不改架构、当天就能做"的事，也是效果差最常见的根因。

### 三种切法

示例里实现了三种，都跑在同一批语料上（6 篇 FAQ，每篇 5 段、约 900 字）：

```java
// ① 按自然段切，段落过长再按句号拆
byParagraph(text, maxLen)

// ② 定长窗口 + 重叠（重叠是为了不让一句话正好被切断）
byFixedWindow(text, size, overlap)

// ③ 整篇一块
whole(text)
```

### 实测：召回不是唯一目标

10 条查询，每条都标注了"答案在哪篇文档的哪句话里"，跑出来的对比：

| 策略 | 块数 | 平均块长 | recall@1 | recall@3 | MRR | 每次注入 prompt |
| --- | --- | --- | --- | --- | --- | --- |
| `paragraph(max=200)` | 36 | 61 字 | 0.70 | **1.00** | 0.833 | **185 字** |
| `fixed(size=60)` | 50 | 58 字 | 0.70 | 0.90 | 0.767 | 178 字 |
| `fixed(size=600)` | 6 | 374 字 | **0.90** | 1.00 | 0.950 | 1130 字 |
| `whole` | 6 | 374 字 | 0.90 | 1.00 | 0.950 | 1130 字 |

三个结论，每个都能直接指导决策：

**一、切大块召回更高，但代价是 6 倍的注入量。**

`fixed(600)` 的 recall@1 是 0.90，`paragraph` 是 0.70 —— 大块确实更容易"包含答案"。但看最后一列：每次检索要往 prompt 里塞 **1130 字**，而小块只要 **185 字**。

换算成钱（第 8 章的模型）：一次问答的输入从约 190 token 变成约 1130 token，**贵 5 倍**。而且答案只占其中 30 来个字，剩下的全是噪声 —— 噪声多了，模型被带偏的概率也上升。

**二、切太碎会漏。** `fixed(60)` 的 recall@3 掉到 0.90 —— 有一条查询**完全找不到**答案（排在 3 名之外）。原因是 60 字的窗口把一句完整的话切成两半，"新疆发货要几天"的答案被拆到了两个块里，谁都不完整。

**三、大块多出来的 recall@1 收益只有 0.2。** 因为 `paragraph` 的 recall@3 已经是 **1.00** —— 答案都在前 3 块里。也就是说，只要 top-k 取 3，两种切法的实际效果没差多少，成本却差 6 倍。

### 所以切多大？

没有标准答案，但有起点：

| 文档类型 | 起点 | 理由 |
| --- | --- | --- |
| FAQ / 政策条款 | **按段落，200–400 字** | 每段就是一个完整语义单元 |
| 技术文档 / 手册 | 按标题层级，一节一块 | 标题本身就是语义边界 |
| 合同 / 法规 | 按条款编号，一条一块 | 条款之间互相引用，不能拆散 |
| 聊天记录 / 日志 | 按会话/时间窗，800–1500 字 | 上下文缺了就答不准 |

两条通用规则：

1. **优先按文档自身的结构切**（段落、标题、条款），结构就是作者已经做好的语义分割，你不需要再猜
2. **无论如何都保留 overlap**（10–20%），它救的是"正好切断一句话"这种倒霉情况

> 这一节的数字来自示例里的替身 embedding（字面重合度），**绝对值不能代表你用真模型的效果**。但结论的形状是通用的：切碎会漏、切大贵、大块多出来的召回要用 6 倍成本换。示例的评测框架可以直接替换成你的语料和真 embedding 重跑。

## 9.3 向量库选型

先破一个执念：**十万条以下的块，用什么向量库都行，差别在你的运维成本。**

| 方案 | 适合谁 | 优点 | 代价 |
| --- | --- | --- | --- |
| **Redis**（RediSearch） | 已经有 Redis、块数 < 百万 | 运维零新增，延迟低 | 内存贵，复杂过滤能力一般 |
| **pgvector** | 已经有 PostgreSQL、要事务一致 | 和业务数据同库，能做 join 和权限过滤 | 百万级以上要调参，索引构建慢 |
| **Milvus / Qdrant** | 千万级、要做多路召回 | 专门的向量库，索引类型多，性能上限高 | 多一个要运维的分布式系统 |
| **云托管**（各家向量检索服务） | 小团队、不想运维 | 开箱即用，按量付费 | 数据出网、成本随量线性涨 |

判断顺序（从第一个问题开始问）：

1. **块数会超过 100 万吗？** 不会 → 别上 Milvus，Redis 或 pgvector 足够
2. **你需要按业务字段过滤吗**（租户、权限、时间）？需要 → pgvector 的 `WHERE` 最省事
3. **你已经有 PostgreSQL 吗？** 有 → 直接 pgvector，少一个组件就是少一类故障
4. **团队没人会运维分布式系统吗？** 没有 → 云托管，把钱花在别处

> 一个反直觉的建议：**先用一张表 + 暴力扫（不建向量索引）跑起来。** 10 万条 768 维向量，一次全表扫描在普通机器上是几十毫秒 —— 而你的模型调用要一秒起。**在向量检索成为瓶颈之前，它根本不是你该优化的地方。**

## 9.4 换 embedding 模型会怎样

这是 RAG 最容易被低估的一次性成本。

### 三个后果

**一、维度不匹配，旧数据不能用。**

```java
// 旧模型 1536 维，新模型 1024 维
float[] v = newEmbedder.embed(text);     // 1024 维
index.search(v);                          // 索引里全是 1536 维 → 直接报错或算出垃圾
```

向量库通常会拒绝维度不一致的**写入**，但**查询时的维度不一致有时不报错** —— 只是结果全乱。这是最坏的失败方式：安静地错。

**二、必须全量重建，没有增量办法。**

同一个文本，两个模型给出的向量在完全不同的空间里，**不能混着比**。所以换模型 = 重算所有块 = 一次全量 reindex。

成本估算：块数 × 平均 token 数 × embedding 单价。10 万个 200 token 的块 = 2000 万 token，按百万 token 几分钱算，**钱是几块，但要跑几小时**（受 RPM 限制，第 6 章那套限流在这里同样要用）。

**三、两个模型的向量不能混用，所以必须双写过渡。**

正确做法：

```
① 新建一个索引（新 collection / 新表 / 新字段）
② 全量灌入新向量，期间旧索引继续服务
③ 灌完、评测通过后，切流量到新索引
④ 观察一天，删掉旧索引
```

**切流量的判据必须是评测，不是"看起来差不多"。** 用 9.2 那个框架，在新旧索引上跑同一批查询，比较 recall@k。

### 一条降低风险的约定

在块表里存两个字段：`embedding_model` 和 `embedding_version`。

```sql
alter table kb_chunk add column embedding_model varchar(64);
```

这样任何时候都能查出"哪些块是用旧模型算的"，重建时按它过滤，也能防止新旧混用 —— 查询时带上模型名，查不到就明确报错，而不是悄悄返回垃圾。

## 9.5 检索不准，四步排查

不要一上来就换模型。按顺序查，每一步都有明确的判据：

**第一步：答案在库里吗？**

在原始文档里搜答案那句话。搜不到 → 文档没同步进来，或者被权限过滤掉了。**这一步能排除掉一半的"检索不准"。**

**第二步：答案被切断了吗？**

搜答案所在的那一段，看它被切成了几个块。如果关键短语跨在两个块里（示例里 `fixed(60)` 就干过这事），检索再好也没用。

判据很简单：**把块打印出来，人工看一遍。** 这一步花十分钟，能省你两天调参。

**第三步：召回到了吗？**

对一批已知答案的问题，算 recall@k：

```
recall@3 = 前 3 个块里包含答案的查询数 / 总查询数
```

低于 0.8 就是检索的问题，不是生成的问题。示例的 `/api/eval` 就是干这个的 —— 换成你的语料，它就是你 RAG 的回归测试。

**第四步：生成对了吗？**

前 3 步都过了、答案还是错，才是 prompt 和模型的问题。常见两种：

- **答案不在开头**：模型对上下文中间的内容利用率最低，把最相关的块排在最前面
- **指令太弱**：没有明确说"只根据资料回答，资料里没有就说没有" —— 不说的话，它一定会编

## 9.6 什么时候不该用 RAG

RAG 不是万能药。三种情况它有更好的替代：

| 场景 | 为什么不合适 | 更该用什么 |
| --- | --- | --- |
| 文档能整篇塞进上下文（5 万字以内，每次都问同一篇） | 检索反而丢信息 | 直接全文塞进去，用长上下文模型 |
| 问题是结构化查询（"上个月华东区退货率"） | 向量检索不懂聚合 | 生成 SQL 去查库，或直接写查询接口 |
| 需要精确匹配（订单号、身份证、错误码） | 向量检索是模糊的 | 关键词/正则先过滤，再做语义排序 |
| 知识更新极快（分钟级） | 索引跟不上 | 直接查实时接口 |

第三条特别常见：用户问"订单 12345 到哪了"，向量检索会召回一堆讲物流政策的段落，而正确答案在第 2 章那个 API 里。

**做法是组合，不是二选一**：先用规则/关键词把范围缩小（识别出订单号就走 API），剩下的才交给语义检索。

## 9.7 结论

三条结论：

1. **切分比模型重要。** 实测：切碎（60 字）recall@3 掉到 0.90，有一条完全找不到；切大（600 字）recall@1 到 0.90，但每次注入 prompt 的字数是小块的 **6.1 倍**。默认按文档结构切，200–400 字，留 10–20% 重叠。
2. **先建评测，再调参数。** 没有 recall@k 的调参全是猜。10–20 条"问题 + 答案在哪个块"就够起步，示例的 `/api/eval` 可以直接改成你的语料。
3. **向量库不是选型的难点，换 embedding 才是。** 十万块以内 Redis/pgvector 都行；但块表里一定要存 `embedding_model`，否则换模型那天你会不知道哪些数据该重建。

可以直接抄的起点：

```yaml
rag:
  chunk:
    strategy: paragraph     # 按结构切，别用定长
    max-chars: 300          # 200–400，按你的文档调
    overlap-chars: 40       # 10–20%
  retrieve:
    top-k: 3                # 够用；再多是噪声和成本
  index:
    embedding-model: bge-m3 # 记进块表，换模型时靠它筛
```
