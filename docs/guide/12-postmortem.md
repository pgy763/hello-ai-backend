# 第 12 章 · 生产事故复盘集

## 这一章解决什么问题

前面 11 章讲的是「怎么搭对」。这一章讲「搭对了也会怎么炸」。

而且这一章的事故**大部分是本书示例在开发过程中真实踩到的** —— 不是编出来的场景。每个都带着实测数字，因为复盘的价值全在细节里。

每一篇结构一样：**现象 → 根因 → 止血 → 根治 → 怎么提前发现**。

## 你会得到

- 10 个带实测数字的事故，覆盖并发、状态、计量、RAG、压测、提示词
- 3 个行业高频模式（密钥泄漏、预算失控、静默降级）
- 一份复盘模板和一份「上线前自检清单」

## 前置

全书。这一章不引入新概念，只把前面踩过的坑重新排一遍。

## 12.1 先说复盘怎么写

一份没用的复盘长这样：

> **事故原因**：开发同学操作失误，误删了数据。**改进措施**：加强培训，提高意识。

问题在最后一句 —— **「加强培训」不是措施，是许愿。** 下次还是会犯，因为你没改任何东西。

一份有用的复盘必须回答五个问题：

| 问题 | 不合格的答案 | 合格的答案 |
| --- | --- | --- |
| 发生了什么 | 「系统挂了」 | 「14:02–14:19，17 分钟内 320 个请求里 220 个失败」 |
| 影响面 | 「部分用户受影响」 | 「所有新建工单，约 40% 的请求失败」 |
| 根因 | 「操作失误」 | 「限流异常未映射到 429，调用方按 500 重试，重试进一步打满配额」 |
| 为什么没早发现 | 「没监控」 | 「失败率监控只看 5xx 总数，没区分 429 和 500」 |
| 改了什么 | 「加强培训」 | 「异常显式映射 429 + Retry-After；压测器区分 429/500/503；告警增加 429 占比」 |

**判断标准很简单：如果改的那条措施不能用一个 PR 描述出来，它就不是措施。**

## 12.2 十个真实案例

下面每一条都来自本书示例的开发过程，数据都是实测的，能在对应章节的示例里复现。

### 案例 1 · 令牌桶「看起来原子」，实际超卖 3 倍

**现象**：容量 10 的桶，40 个并发请求，**放行了 40 个**（超卖 30 个）。

**根因**：第一版写成「先读令牌数 → 计算补充 → 判断够不够 → 再写回」：

```java
// 错：读和写不在一个临界区
double now = bucket.get();          // 1. 读
if (now >= 1) {
    bucket.set(now - 1);            // 2. 写  ← 这中间别人也能进来
    return true;
}
```

换成 `AtomicLong` 也没用 —— **问题不在单个操作，在于「读-改-写」这个组合不是原子的**。

**止血**：把整个判断包进一个 `synchronized` 方法。

**根治**：`synchronized tryTake()`；跨进程用 Redis + Lua（第 6 章）。

**怎么提前发现**：压测时**统计放行数**，和桶容量对比。「10 个令牌放行 40 个」是压一下就能看见的。

> 这个 bug 只在并发下出现，本地跑一次永远是对的。**「我本地测过了」这句话在并发面前没有意义。**

### 案例 2 · 强杀进程后，任务重跑了最后一步

**现象**：一个三步任务，在第三步刚做完时 `kill -9`，重启后第三步**被重跑了一遍**。

**根因**：H2 默认有约 1 秒的写延迟（`WRITE_DELAY`），最后一条 `SUCCEEDED` 还在内存里没落盘。

```java
// 看起来很正常的一条更新
update task_step set status = 'SUCCEEDED' where id = ?
```

**止血**：JDBC URL 加 `WRITE_DELAY=0`。

```
jdbc:h2:file:./data/taskdb;MODE=MySQL;WRITE_DELAY=0
```

**根治**：理解这条的等价物 —— MySQL 的 `innodb_flush_log_at_trx_commit`、PostgreSQL 的 `synchronous_commit`。**「事务提交了」不等于「落盘了」。**

**怎么提前发现**：压测里加一条「执行到一半 `kill -9` 再重启」的用例。这条用例不写，你永远发现不了。

### 案例 3 · 流式响应的成本，少了 12.6%

**现象**：流式调用的 token 统计，比非流式少了 **12.6%**（估算 139，真实 159）。

**根因**：流式响应默认**不返回 usage 字段**，只能按字符数估算；而中文按「字符数 ÷ 1.75」折算本身就偏保守。

```java
// 没有 usage 时的兜底估算
int estimated = (int) Math.round(chars / 1.75);
```

**止血**：请求里带上「返回 usage」的参数（不同厂商叫法不同，比如 `stream_options: {include_usage: true}`）。

**根治**：两件事一起做 —— ① 开启 usage；② 保留估算作为兜底，并在日志里标记 `tokens_estimated = true`。

**怎么提前发现**：定期「同一段文本，流式 vs 非流式」对账，差异超过 5% 就查。

> 12.6% 的偏差不足以让任何人报警，但一年下来是 12.6% 的预算。

### 案例 4 · 成本报表全是 0

**现象**：`/api/cost` 返回 `costYuan: 0`，但 `cost_micros` 明显不是 0。

**根因**：H2 返回的列名是**大写**（`COST_MICROS`），代码按小写取（`cost_micros`），取到 null，被当成了 0。

```java
// 错：H2 返回的 key 是 COST_MICROS
long micros = (long) row.get("cost_micros");
```

**止血**：统一转小写。

```java
row.forEach((k, v) -> out.put(k.toLowerCase(), v));
```

**根治**：数据访问层统一做列名归一化，不要在每个调用点手写 key。

**怎么提前发现**：**「金额是 0」必须当成 bug，不能当成「还没消费」。** 加一条断言：有调用记录时总成本必须大于 0。

> 金额类的 0 是最危险的默认值 —— 它看起来像"正常"，所以没人查。

### 案例 5 · 切太碎，答案被切成两半

**现象**：检索召回率在 `fixed(60)` 切法下掉到 **0.90**，有一条查询**完全找不到**答案。

**根因**：60 字的定长窗口把「答案那句话」切到了两个块里，两块都不完整，所以哪块都不匹配。

**止血**：切法改成按段落（`paragraph`），召回率回到 1.00。

**根治**：按文档自身结构切（段落/标题/条款），并且无论如何留 10–20% 重叠。

**怎么提前发现**：把块打印出来人工看一遍（第 9 章的 `/api/chunks`）。**十分钟能省两天调参。**

> 没有 recall@k，你会以为是模型不行，然后去换更贵的模型 —— 而问题在切分。

### 案例 6 · 改了权限没重建索引，普通用户看到了财务文档

**现象**：把文档 d2 的权限从 `finance` 改成 `public`，普通用户 alice 立刻能搜到它；反过来（`public` → `finance`）时，alice **仍然能搜到** —— 这是越权。

**根因**：权限是**存在块里的副本**。改了文档表，块里还是旧权限；不重建索引，检索时用的就是旧权限。

```java
// 错误：只改文档，不重建
docs.put(docId, newDoc);
// 块还是旧的 → 检索按旧权限过滤 → 越权
```

**止血**：权限变更也标记为「需要重建」。

```java
if (contentSame && metaSame) return "跳过";
// 内容没变但元数据变了 —— 也必须重建
```

**根治**：如果权限频繁变，别把权限字符串存进块，改存**权限组 ID**（组成员变更不需要重建）。

**怎么提前发现**：写一条断言测试 ——「降权后，无权限用户搜不到」。这条测试比任何 code review 都可靠。

> **这是本书里最危险的一个 bug**：不报错、不告警、不影响功能，只在你被审计的那天爆发。

### 案例 7 · 删了文档，检索还在召回它

**现象**：文档 d2 已从文档表删除，但检索结果里仍然出现它的块。

**根因**：删除只删了文档记录，**没有删块**。

**止血**：`delete` 里连带清理块和向量。

**根治**：加一个「孤儿块对账」定时任务 —— 定期扫「块表里有、文档表里没有」的记录。

**怎么提前发现**：删除接口的返回值里带上「连带清理了多少块」。删完是 0 块，说明你没清。

> 「删除」永远比「新增」容易漏。**新增时你会测，删除时你不会。**

### 案例 8 · 限流返回了 500，压测时看起来像服务挂了

**现象**：把上游配额卡到每分钟 100，压测 320 个请求 —— 220 个失败，但全是 500，不是 429。

**根因**：限流异常抛的是普通 `RuntimeException`，Spring 默认映射成 500。

**止血**：显式映射。

```java
@ExceptionHandler(RateLimited.class)
public ResponseEntity<?> limited(RateLimited e) {
    return ResponseEntity.status(429).header("Retry-After", "60").body(...);
}
```

**根治**：错误码分三类，各有不同的客户端行为：

| 状态码 | 含义 | 客户端应该做什么 |
| --- | --- | --- |
| 429 | 配额用完 | 等待 `Retry-After` 秒 |
| 503 | 上游过载 | 退避后重试 |
| 500 | 我方 bug | 重试也没用，告警 |

**怎么提前发现**：压测器分别统计 429 / 500 / 503。混在一起统计，你就看不出是限流还是故障。

> 返回 500 的后果是**放大**：调用方重试 → 重试打满配额 → 配额又触发 500，一个正反馈循环。

### 案例 9 · 压测器自己把自己锁死了

**现象**：并发设为 1 时，压测一个请求都发不出去，超时。

**根因**：

```java
// 错：把压测线程池交给了 HttpClient
ExecutorService pool = Executors.newFixedThreadPool(concurrency);
HttpClient client = HttpClient.newBuilder().executor(pool).build();
```

并发为 1 时，唯一的线程阻塞在 `client.send()`，而 `client` 内部也需要这个线程来完成请求 —— **自锁**。

**止血**：不传 `executor`，用默认执行器。

**根治**：压测器加自检 —— **平均在飞请求数 ≈ 并发数**（利特尔法则）。对不上就是压测器有问题。

**怎么提前发现**：这条自检现在就在示例里（第 11 章的 `avgInFlight`）。**压测工具本身也要被验证**，否则你压出来的数字全是假的。

### 案例 10 · 分类结果全错，因为提示词里带了答案

**现象**：三张工单（退款、专票、物流）分类结果**全是「退款」**。

**根因**：分类指令是这么写的：

```
请给下面这条工单分类（退款/发票/物流/会员/其他），只输出类别：
<工单内容>
```

模型会从**整个 prompt** 里找关键词 —— 指令里的「退款」排在第一位，永远匹配上。

**止血**：指令里不出现类别名。

```
为下面的工单选一个类别，只输出类别名称：
<工单内容>
```

**根治**：**任何「指令 + 数据」拼接的地方，都要假设模型分不清哪部分是指令。** 结构化一点的做法是用分隔符或 JSON 字段把数据包起来。

**怎么提前发现**：分类/抽取类接口**必须用一批已知答案的样本跑准确率**。三条样本就能发现「全错」。

> 这是**提示词 bug**，不是模型能力问题。换更贵的模型只会让它错得更自信。

## 12.3 三个行业高频模式

下面三个是行业内反复出现的模式，**不是本书示例的实测**，但值得知道。

### 模式 A · 密钥进了 git 历史

**现象**：有人把 `sk-xxx` 提交进仓库，发现后删掉了当前代码 —— 但密钥已经泄漏。

**为什么删代码没用**：

```bash
git log -S "sk-" --oneline     # 有输出 = 历史里有
```

**根治**：① 立刻**吊销**密钥（不是删除文件，是吊销）；② 用 `git filter-repo` 清历史；③ 加 pre-commit 钩子扫描；④ 密钥只从环境变量读。

**教训**：**发现泄漏的第一件事是吊销，不是清理。** 清理要几小时，吊销只要一分钟。

### 模式 B · 一个死循环刷掉一个月预算

**现象**：某个重试逻辑没写上限，上游超时 → 重试 → 再超时 → 再重试，一夜之间烧掉整月预算。

**根治**：三层防线 ——

1. **单请求**：重试上限 3 次 + 指数退避（第 5 章）
2. **单业务线**：日预算上限，超了直接拒绝（第 4 章的虚拟密钥额度）
3. **全局**：日成本告警 + 硬上限（第 8 章的计量）

**教训**：**成本必须有硬上限，不能只有告警。** 告警在凌晨三点没人看得到，硬上限会自己生效。

### 模式 C · 升级框架后，流式静默失效

**现象**：升级 Spring Boot 或某个 SDK 后，接口还能返回数据，但**不再流式**了 —— 用户等 8 秒才看到全部内容。

**为什么难发现**：功能没坏，测试全过，只有「首字节时间」变了。

**根治**：加一条回归测试，断言**首字节时间 < 1 秒**（第 2 章的验证方法）。功能测试测不出这个，只有指标测试能。

**教训**：**「能用」和「用得对」之间，隔着一个指标。**

## 12.4 复盘模板

把这段抄走，下次直接用：

```markdown
## 事故：<一句话描述>

**影响**：<谁、多久、多少比例>。例：14:02–14:19，所有新建工单，约 40% 失败
**级别**：P0（全站不可用）/ P1（核心功能受损）/ P2（体验下降）

### 时间线
| 时刻 | 事件 |
| --- | --- |
| 14:02 | 告警：工单失败率 40% |
| 14:05 | 定位到限流异常返回 500 |
| 14:12 | 止血：映射 429 |
| 14:19 | 失败率回落到 0.1% |

### 根因
<一句话说清因果链，不要写「操作失误」>

### 为什么没早发现
<监控缺了什么？测试缺了什么？>

### 改了什么
- [ ] <能用 PR 描述的具体改动，带负责人和期限>
- [ ] <监控/告警的补充>

### 沉淀
<能写进 checklist 的一条规则>
```

## 12.5 上线前自检清单

这十条是从上面所有事故里反推出来的，**每条都能用一条命令或一个接口验证**：

- [ ] 并发下不超卖：压测时统计放行数，对比桶容量（案例 1）
- [ ] 强杀后不重跑：执行到一半 `kill -9`，看状态（案例 2）
- [ ] 流式计量对得上：流式 vs 非流式对账，差异 < 5%（案例 3）
- [ ] 金额不为 0：有调用记录时总成本 > 0（案例 4）
- [ ] 切分不切断：打印块人工看一遍（案例 5）
- [ ] 降权即失效：改权限后无权限用户搜不到（案例 6）
- [ ] 删除即消失：删文档后检索不再召回（案例 7）
- [ ] 限流返回 429：压测器分别统计 429/500/503（案例 8）
- [ ] 压测器自检：在飞请求数 ≈ 并发数（案例 9）
- [ ] 分类准确率：用已知答案的样本跑一遍（案例 10）

## 12.6 结论

三条结论：

1. **事故几乎都出在「组合」上，不在「组件」上。** 令牌桶单测没问题、并发下超卖；删除接口单测没问题、和检索组合就召回已删文档。**测单个类不够，要测流程。**
2. **最危险的 bug 不报错。** 权限不重建（越权）、计量少 12.6%、删除不干净 —— 这三个都不抛异常，只会安静地错。
3. **复盘的价值在「改了什么」，不在「发生了什么」。** 如果改的那条措施写不成一个 PR，就说明你没改任何东西。
