## 这一章解决什么问题

第一个模型接完了。现在业务方说：便宜的活给 A 模型，难一点的给 B 模型，别的地方已经在用 C 了。

于是你的代码里开始出现到处散落的 `if (model.equals("xxx"))`。

## 你会得到

- 一个 Provider 抽象，业务层只写一句话，换厂商不改业务代码
- 配置驱动的模型注册表，新厂商接进来只改 `yaml`
- 一份「所谓 OpenAI 兼容」的真实兼容性差异清单

## 提纲

- **3.1 为什么一定会变成多模型** —— 成本、能力差异、可用性，三个无法回避的原因
- **3.2 OpenAI 兼容协议：事实标准，但它不保证兼容** —— 真兼容了什么，哪些地方会翻车
- **3.3 Provider 接口怎么设计** —— 一个方法还是三个方法？把流式和非流式分开的理由
- **3.4 注册表与配置化** —— 从 `application.yml` 到运行时路由
- **3.5 兼容性差异实录** —— 不同厂商在 `system` 角色、`temperature` 范围、`finish_reason`、错误码上的实际差异
- **3.6 结论** —— 抽象到什么程度就该停手
