# 第 13 章 · 面试题：AI 后端工程师会被问到的 30 问

## 这一章解决什么问题

「AI 后端工程师」的面试，和普通 Java 后端不一样。

普通后端问的是「你怎么扛住流量」。AI 后端问的是「**上游不受你控制时，你怎么让它看起来像受你控制**」—— 延迟、质量、成本、配额，四个都不在你手里，但你得对结果负责。

这 30 道题覆盖了这本书的全部要点。**每道题都标了出处**，答不上来就回去看那一章。

## 你会得到

- 30 道题，每题给出「面试官在考什么」「参考答案」「常见陷阱」
- 一条区分线：哪些是背八股能答的，哪些是**做过才答得出**的

## 怎么用

- **准备面试**：先自己答一遍，再看答案。答得顺的跳过。
- **面试复盘**：被问住的题，回对应章节补。
- **自测**：30 题能答对 20 题以上，说明这本书你读进去了。

> 提醒：答案里的数字都来自本书示例的实测。**面试时报数字，但要能说清数字是怎么来的** —— 否则一追问就露馅。

## 一、接入与协议（第 1–3 章）

### 1. 你们的 AI 接口首字节延迟是多少？怎么优化的？

**考什么**：有没有真上过流式。只答「加了缓存」基本可以判定没做过。

**参考**：流式（SSE）下首字节就是模型开始吐字的时刻，通常 200–800ms；非流式要等全部生成完，2–8 秒。优化手段：

- 流式输出（最大的那一刀，通常 5–10 倍体感提升）
- 减少 prompt 长度（每 1000 token 约 100–300ms 的 prefill）
- 就近接入 / 连接复用
- 小模型先出草稿（投机执行）

**陷阱**：说「加了 Redis 缓存」。LLM 请求天然难缓存，答这个会暴露你没做过。

### 2. 你们怎么统一多家模型的差异？

**考什么**：抽象能力。答「写 if-else」是初级答案。

**参考**：一个 Provider 接口 + 一个「差异翻译层」。差异集中在五处：**认证方式、请求体结构、流式事件格式、错误码、usage 字段位置**。翻译层把厂商格式转成内部统一格式，业务只认内部格式。

关键设计：**接口只暴露能力，不暴露厂商**。业务代码里不该出现 `if (provider == "openai")`。

### 3. 换模型的时候，业务代码要改多少？

**考什么**：你的抽象是不是真的成立。

**参考**：**零改动**。如果换模型要改业务代码，说明抽象漏了 —— 常见漏点：

- 把 usage 字段当业务字段用（不同厂商字段名不同）
- 依赖某家的特殊参数（`temperature` 范围、`max_tokens` 语义）
- 错误码直接透传给业务

**自检方法**：假装明天要接一家新厂商，数一下要改几个文件。超过 3 个就有问题。

### 4. 流式输出断了，前端怎么知道是正常结束还是出错？

**考什么**：SSE 的工程细节。

**参考**：SSE 有明确的结束语义 —— 服务端发 `data: [DONE]` 后关连接。所以：

- 收到 `[DONE]` = 正常结束
- 连接断了但没收到 `[DONE]` = 异常，前端应该重试或提示

**陷阱**：只靠「连接关闭」判断结束。代理超时、网关断流都会关闭连接，那会被误判成正常结束，用户看到半句话还以为说完了。

### 5. 一次请求最长能等多久？超时怎么设？

**考什么**：超时链的设计。

**参考**：三层超时，从内到外递增：

```
上游读超时    60s   （长回答可能 30s+）
业务处理超时  90s
网关/客户端   120s
```

**关键**：上游超时必须小于业务超时，否则业务层永远等不到自己的超时。**最外层超时一旦触发，内层的重试就白做了。**

### 6. 用户重复点提交按钮，会不会重复计费？

**考什么**：幂等。

**参考**：三道防线：

1. 前端 disabled（最弱，防不了重放）
2. 幂等键（客户端生成 `request_id`，服务端做唯一约束）
3. 数据库唯一索引兜底

**陷阱**：用「请求内容 hash」做幂等键。用户真的想问两遍同一个问题时，会被误判成重复。

## 二、稳定性（第 5–7 章）

### 7. 主模型挂了怎么办？

**考什么**：降级链。

**参考**：主 → 备 → 兜底（缓存/模板/人工）。但**关键是「怎么判断它挂了」**：

- 按错误类型降级，不按状态码一刀切（400 参数错不该降级）
- 连续 N 次失败才切（单次抖动不切）
- 恢复要探测（半开状态）

**陷阱**：答「超时就切」。追问「超时阈值多少、误判过吗」就露馅 —— 阈值太敏感会把好请求也降级，第 5 章实测过。

### 8. 降级之后的质量怎么保证？

**考什么**：你有没有想过降级的代价。

**参考**：三件事：

1. **打标记**（provider 字段），事后能筛出降级期间的回答
2. **限制降级范围**（简单分类可以降，合同条款不行）
3. **降级即告警**（降级不是正常状态，是异常状态）

第 14 章实测：降级到小模型后单工单成本从 0.0007 元降到 0.0001 元（省 86%），**但质量差异你不知道** —— 所以必须留痕。

### 9. 熔断器的三个状态是什么？半开为什么要限制并发？

**考什么**：熔断的实现细节。

**参考**：CLOSED（正常）→ OPEN（拒绝）→ HALF_OPEN（探测）。

半开**必须限制探测并发**（比如只放 1 个），否则：恢复瞬间几十个请求同时涌入，全部失败，又被打回 OPEN —— 这叫「半开被打穿」。

**陷阱**：只答三个状态的名字。追问「半开和关闭的区别」就答不上来。

### 10. 限流怎么做？单机够吗？

**考什么**：限流的层次。

**参考**：单机令牌桶管「保护自己」，分布式 Redis + Lua 管「保护配额」。两层都要：

- 本地桶：容量小、响应快，防突发
- 分布式桶：全局配额，防超额

**陷阱**：只答单机。多实例部署时单机限流等于没限流（N 个实例就是 N 倍）。

### 11. 令牌桶和漏桶的区别？你们用哪个？

**考什么**：基础，但答错的人不少。

**参考**：

| | 令牌桶 | 漏桶 |
| --- | --- | --- |
| 允许突发 | 可以（桶里攒着令牌） | 不行（匀速流出） |
| 典型场景 | API 限流 | 流量整形 |

LLM 场景用**令牌桶**，因为需要允许短时突发（用户一次性点几下）。

### 12. 多步任务跑到一半服务重启了，怎么办？

**考什么**：状态机与断点续跑。

**参考**：状态落库 + 每步独立提交 + 已完成步骤不重跑。

第 7 章实测：三步任务在第二步失败，重启后**只重跑第二步**（上游总调用 3 次，而不是从头 5 次）。

**陷阱**：答「加重试」。追问「重试到第几步，前面的钱谁出」就答不上来了。

### 13. 任务卡在「处理中」永远不动，怎么排查？

**考什么**：僵尸任务的识别。

**参考**：非终态必须有超时回收。做法：

- 记录 `started_at` + `lease_seconds`
- 定时任务扫「超时未完成」→ 重置为待处理
- 加心跳（长任务定期续租）

**为什么难发现**：它不报错，只是任务列表里越来越多「处理中」。

### 14. 怎么保证同一个任务不被两个实例同时处理？

**考什么**：并发控制。

**参考**：CAS 抢占。

```sql
update task set status='RUNNING', owner=? where id=? and status='PENDING'
```

影响行数 = 1 才算抢到。第 7 章实测：3 个并发恢复请求，只有 1 个 `claimed=true`。

## 三、成本与计量（第 4、8 章）

### 15. 怎么控制成本？

**考什么**：有没有真算过账。

**参考**：五个层次，从便宜到贵：

1. **减少调用**（缓存、批处理，最有效）
2. **减少 token**（精简 prompt、截断历史）
3. **换小模型**（按任务难度路由）
4. **提升缓存命中**（前缀缓存，实测降 21%）
5. **套餐比价**（同样的量换套餐）

**陷阱**：只答「用便宜的模型」。那不叫控制成本，那叫降低质量。

### 16. 你们怎么知道钱花在哪了？

**考什么**：token 归因。

**参考**：每次调用落一条明细，至少四个字段：

```
trace_id / tenant（谁）/ model（哪个模型）/ cost_micros（多少）
```

有了这四个才能回答「哪个业务线最费钱」「哪个功能最不划算」。

**关键**：成本必须能**拆到单次请求**，否则你只能看总数，无法优化。

### 17. 流式调用的 token 怎么统计？

**考什么**：踩过这个坑没有。

**参考**：流式默认不返回 usage，要做两件事：

1. 请求里开启 usage 回传（如 `stream_options.include_usage`）
2. 保留字符数估算做兜底，并标记 `tokens_estimated`

第 8 章实测：不开启时估算偏低 **12.6%**（139 vs 159）。这个偏差不会触发任何告警，但它一直在。

### 18. 缓存能省多少？

**考什么**：有没有量化过。

**参考**：前缀缓存（prompt caching）命中后，输入 token 按更低的价计费。第 8 章实测：800 token 的固定前缀命中后，单次成本从原价降到 **4530 微元，降 21%**。

**前提**：前缀必须**逐字节相同**，且放在最前面。把可变内容（时间戳、用户名）放在前面会让缓存全失效。

### 19. 预算超了怎么办？

**考什么**：有没有硬上限。

**参考**：三层：

1. **单请求**：max_tokens 上限 + 重试上限
2. **单租户**：日额度，超了 429
3. **全局**：日预算告警 + **硬熔断**

**关键**：**硬上限不能只有告警。** 凌晨三点没人看告警，硬上限会自己生效。

## 四、RAG 与数据（第 9、10 章）

### 20. RAG 检索不准，你怎么排查？

**考什么**：排查路径，不是调参技巧。

**参考**：四步，每步有判据：

1. 答案在库里吗（原文搜一遍）
2. 被切断了吗（打印块人工看）
3. 召回到了吗（算 recall@k，低于 0.8 就是检索问题）
4. 生成对了吗（前三步都过了才查 prompt）

**陷阱**：一上来就换更大的模型。**大部分 RAG 问题是切分，不是模型。**

### 21. 切分切多大？为什么？

**考什么**：有没有实测过。

**参考**：没有标准答案，但有起点：**按文档结构切，200–400 字，留 10–20% 重叠**。

第 9 章实测（10 条查询）：

| 切法 | recall@3 | 每次注入 |
| --- | --- | --- |
| 按段落（61 字/块） | 1.00 | 185 字 |
| 定长 60 | 0.90 | 178 字 |
| 定长 600 | 1.00 | **1130 字** |

结论：切太碎会漏（0.90），切太大召回没提升但贵 6 倍。

**陷阱**：答「512 token 是业界标准」。说不出为什么，也不知道自己语料该切多少。

### 22. 文档更新了，索引怎么更新？

**考什么**：增量索引。

**参考**：**用内容哈希判断，不要用时间戳**。时间戳两个方向都会骗你：

- 时间戳变了内容没变（后台点保存）→ 白算一遍
- 时间戳没变内容变了（直接改库）→ 索引是旧的

第 10 章实测：只改 1 篇，embedding 只重算那 1 篇（增量 3 次，而不是 6 次）。

### 23. 权限怎么过滤？放在检索前还是检索后？

**考什么**：有没有意识到这是数据事故的红线。

**参考**：**检索时过滤**（不是索引时建多份）。但有个坑：

- 先过滤再检索：可能过滤到只剩几条，召回质量下降
- 先检索再过滤：top-k 可能全被过滤掉，返回空

**做法**：权限条件下推给向量库（pre-filter）；如果向量库不支持，把 top-k 放大（10 → 50）再过滤。

### 24. 改了文档的权限，索引要重建吗？

**考什么**：这是本书最危险的一个坑。

**参考**：**必须重建**。因为权限是存在块里的副本，不重建的话块里还是旧权限。

把 `public` 改成 `finance` 而没重建 → **普通用户仍然能搜到财务文档 —— 越权，且不报错。**

**根治**：权限频繁变的话，存**权限组 ID** 而不是权限字符串。

### 25. 删除文档要做什么？

**考什么**：细节意识。

**参考**：**连带删块**。只删文档记录的话，检索仍会召回已删除的文档。

再加一层：**孤儿块对账**定时任务，扫「块表有、文档表没有」的记录。

**陷阱**：只答「删数据库记录」。追问「向量库里的块呢」就答不上来。

## 五、架构与容量（第 11 章）

### 26. 你们的系统能扛多少并发？

**考什么**：有没有算过，而不是拍脑袋。

**参考**：`并发 = QPS × 单请求耗时`（利特尔法则）。

LLM 接口耗时 2.5 秒，100 QPS 就需要 250 个并发 —— 是普通接口（50ms）的 50 倍。

所以正确的答法是反过来说：**上游给我 50 个并发，我只能扛 20 QPS**（50 ÷ 2.5）。

### 27. 压测怎么做？和普通接口有什么不同？

**考什么**：方法论的差异。

**参考**：三个不同：

1. **耗时差 50 倍** → 并发需求差 50 倍
2. **瓶颈在上游** → 加线程只是加排队
3. **成本按 token** → 压真模型是在烧钱

**做法**：先用假上游把自己的接入层压穿（免费），再用真上游小流量验证。

第 11 章实测：并发 8 → 19.47 RPS / P95 417ms；并发 64 → 19.78 RPS / P95 **3248ms**。**吞吐不变，延迟涨 7.8 倍。**

### 28. 系统变慢了，你怎么定位是哪里慢？

**考什么**：可观测性。

**参考**：拆三段计时 —— 排队、上游首字节、上游总时长。三段的比例决定优化方向：

- 排队久 → 并发不够 / 上游配额不够
- 首字节久 → prefill 慢（prompt 太长）
- 总时长久 → 输出太长（max_tokens 太大）

**关键**：日志里必须有这三段的耗时，事后才有得查。

### 29. 怎么保证上线不炸？

**考什么**：上线策略。

**参考**：四件事：

1. **灰度**（按租户/用户百分比切）
2. **可回滚**（配置开关，不是重新部署）
3. **有基线指标**（P95、失败率、成本/请求）
4. **有熔断**（指标劣化自动回滚）

**陷阱**：答「测试覆盖率高」。AI 的行为不是确定性的，测试覆盖率解决不了「答得不好」这类问题。

### 30. 什么时候不该用 AI？

**考什么**：判断力，也是最高级的一题。

**参考**：四种情况：

| 场景 | 为什么不用 | 替代 |
| --- | --- | --- |
| 精确匹配（订单号、错误码） | 模型会算错 | 规则/正则/SQL |
| 结构化查询（统计、聚合） | 模型不懂聚合 | 生成 SQL |
| 文档能整篇塞进上下文 | 检索反而丢信息 | 长上下文直塞 |
| 延迟敏感（<200ms） | 模型做不到 | 缓存/预计算 |

**加分项**：说出「组合而不是二选一」—— 先规则缩小范围，剩下才交给模型。
