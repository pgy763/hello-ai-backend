# 第 10 章 · 把 RAG 接进 Java 服务

## 这一章解决什么问题

上一章的示例是"把 6 篇文档灌进索引，然后搜"。真实系统里，那 6 篇会变成 6 万篇，而且：

- **文档会改**：产品改了退款政策，旧索引里还是老条款，模型会一本正经地告诉用户"14 天无理由"
- **文档会删**：下架的商品文档还在索引里，检索照样召回
- **文档会新增**：新员工入职手册上传了，但没人跑索引，等于没上传
- **权限不一样**：财务文档不能给客服看，但检索层不知道谁在查
- **会失败**：某个 PDF 解析不出来，重试三次还失败，然后就没人管了

一次性脚本处理不了这些。**你需要的是流水线：有状态、能重试、能增量、能清理。**

这一章就做这条流水线。它比想象中简单 —— 难的从来不是技术，是**想清楚"变"这件事有哪几种**。

## 你会得到

- 增量索引的正确判据（内容哈希，不是时间戳），实测只重算改动的那一篇
- 三个必踩的坑：改了权限不重建、删文档不删块、失败没有终点
- 权限过滤应该放在哪一层，以及放错了会怎样
- 一条最小的流水线：`pending → 处理 → indexed / failed → dead → 人工重入`

## 10.1 脚本和流水线的差距

一个"能跑"的索引脚本大概是这样：

```java
for (File f : files) {
    String text = parse(f);
    for (String chunk : split(text)) {
        vectorStore.insert(chunk, embed(chunk));
    }
}
```

它能跑，但只在你第一次跑的时候能跑。差距在这五件事上：

| 差距 | 脚本的做法 | 流水线要做的 |
| --- | --- | --- |
| 增量 | 每次全量重灌 | 判断哪些文档真的变了 |
| 失败 | 抛异常，整批停下 | 单个文档失败不影响其他，记下重试次数 |
| 进度 | 没有 | 每篇文档一个状态，断了能接着跑 |
| 删除 | 不处理 | 文档没了，它的块也要没 |
| 限流 | 无脑打 | 受 embedding 的 RPM 限制（第 6 章） |

每一条都对应一个真实事故。下面一条条补。

## 10.2 判断"变了没"：用内容哈希，别用时间戳

最直觉的做法是比对 `updated_at`：比上次索引时间新，就重建。

**这个判据会在两个方向上都出错。**

**误判一：时间戳变了，内容没变。** 有人在后台点了保存、改了个错别字又改回来、同步任务整点刷新了 `updated_at` —— 这些都会让一篇没变的文档重算一遍。6 万篇文档的库，一次全量重算几小时。

**误判二：时间戳没变，内容变了。** 直接改数据库、批量导入没更新 `updated_at`、或者两个系统时钟不一致。这种更糟：**文档更新了，索引还是旧的**，模型会拿着过期信息回答，而且你还以为自己索引是最新的。

正确判据只有一个：**内容本身有没有变。**

```java
String hash = sha256(doc.content());      // 内容指纹
if (hash.equals(state.indexedHash())) {
    return "跳过：正文和元数据都没变";
}
```

实测（3 篇文档、首次索引 6 次 embedding 调用）：

```
① 首次索引         → processed=3, embedCalls=6
② 改 d2 的正文      → 只有 d2 变 PENDING
③ 再索引           → processed=1, embedCalls 6→9（增量 3，只重算 d2 的块）
④ 内容不变再灌一次   → "跳过：正文和元数据都没变"，embedCalls 不动
```

**只改一篇，就只花一篇的钱。** 这就是哈希判据的价值。

> 存哈希比存时间戳多一个字段，但它带来两个能力：判断"要不要重建"和判断"重建完了吗"。后者是断点续跑的前提（第 7 章那套）。

## 10.3 坑一：改了权限不重建 = 越权

这个坑很隐蔽，因为**它不报错**。

权限信息存在哪？两种做法：

```java
// 做法 A：块里存一份权限副本（索引时写死）
record Chunk(String docId, String text, String permission) {}

// 做法 B：块里不存权限，检索时 join 文档表
```

做法 B 看起来更"正确"（元数据单一来源），但检索时就多一次 join，在向量库里通常做不到 —— 所以绝大多数实现选了做法 A。

**选了 A，就必须接受一个约束：权限变了也要重建索引。**

因为块里存的是**索引那一刻**的权限。你把 d2 从 `finance` 改成 `public`，但没重建，块里还是 `finance` —— 用户 alice 依然搜不到它。

反过来更可怕：把 `public` 改成 `finance`，没重建，块里还是 `public` —— **普通用户能搜到财务文档。这是数据事故，不是 bug。**

示例里把这条写成了显式判断：

```java
if (contentSame && metaSame) {
    return "跳过：正文和元数据都没变";
}
if (contentSame) {
    // 权限存在块的副本里，改了权限不重建索引，检索时用的还是旧权限
    states.put(doc.id(), new IndexState(doc.id(), "PENDING", 0, null, null, 0));
    return "已排队：元数据变了（权限/标题），必须重建，否则块里还是旧权限";
}
```

实测：

```
改 d2 权限 finance → public（正文完全没动）
  → "已排队：元数据变了（权限/标题），必须重建，否则块里还是旧权限"
  alice 搜『专票』（重建前）: 只有 d1（她看不到 d2）
  alice 搜『专票』（重建后）: d2, d2, d2
```

### 更彻底的做法

如果权限会频繁变（比如组织架构调整），就别把权限存进块。改存**权限组 ID**：

```
块里存: group_id = "g-finance"
检索时: 先算出用户能看哪些 group（一次查询），再用这个集合过滤
```

组 ID 比权限字符串稳定得多，改组成员不用重建索引。

## 10.4 坑二：删文档不删块

```java
synchronized String delete(String docId) {
    if (docs.remove(docId) == null) return "文档不存在";

    List<Chunk> removed = chunksByDoc.remove(docId);
    if (removed != null) {
        removed.forEach(c -> vectors.remove(key(docId, c.seq())));   // ← 容易漏
    }
    states.remove(docId);
    return "已删除，连带清理 " + (removed == null ? 0 : removed.size()) + " 个块";
}
```

漏了这一步的后果不是"报错"，是**检索到一个已经不存在的文档**。用户问"这个商品怎么退"，模型引用了一条早就下架的条款 —— 而且你查文档表发现它确实删了，于是开始怀疑人生。

实测：

```
删除 d2: "已删除，连带清理 2 个块"
删除前 carol 搜『发票』: d2, d2, d3, d1, d1
删除后 carol 搜『发票』: d3, d1, d1, d3          ← d2 彻底消失
```

**两个工程上的建议：**

1. **软删除 + 定期清理**。`delete` 只改标记，检索时过滤掉；后台任务按标记清理向量。这样误删可以恢复。
2. **加一个对账任务**：定期扫"块表里有、文档表里没有"的孤儿块。上面那个 bug 之所以难查，就是因为没有任何东西会主动发现它。

## 10.5 权限过滤：放在检索时，不是索引时

两种放法，差别很大：

| 放法 | 做法 | 问题 |
| --- | --- | --- |
| 索引时 | 给每个人建一份索引 | 用户数 × 文档数，存储爆炸 |
| **检索时** | 一次索引，检索时按用户权限过滤 | 需要一个能带过滤条件的检索 |

**必须是检索时。** 索引时那种做法只有在"权限维度极少"时才可行（比如只有 3 个部门，建 3 份索引）。

实测（同一批文档、同一个查询，三个用户看到的不同）：

```
搜『框架协议』
  alice  可见 public            → d1, d1              （没看到，因为她没权限）
  bob    可见 public/finance    → d1, d1              （同上）
  carol  可见 public/finance/cs → d3, d3, d1, d1      （d3 排第一，正确答案）
```

注意 alice 和 bob **不是"答案为空"，是"拿到了不相干的 d1"** —— 因为过滤之后剩下的块里没有真正相关的，检索只能返回次优的。

这个行为要在产品上处理：**如果 top-1 的相似度低于阈值，就直接回答"没有找到相关资料"，别硬答。** 硬答就是编。

### 过滤条件的性能陷阱

带 `WHERE` 的向量检索有一个坑：**先过滤再检索**，可能过滤到只剩几十条，索引白建；**先检索再过滤**，可能 top-10 全被过滤掉，返回空。

两种做法都要有兜底：

```
先过滤再检索（推荐）：把权限条件下推给向量库，走 pre-filter
   ↑ 要求向量库支持带过滤的 ANN 检索（pgvector / Qdrant / Milvus 都支持）
先检索再过滤：把 top-k 放大（比如 10 → 50），过滤后再截断到 3
```

## 10.6 坑三：失败要有终点

一个文档解析失败，会发生什么？

```java
// 天真写法
try { index(doc); } catch (Exception e) { log.error("失败", e); }
```

结果：下一轮调度它又被捞出来、又失败、又记一条日志。**每天 288 条重复日志，文档永远缺一块，没人知道。** 这叫"失败没有终点"。

正确做法：**记次数，有上限，到上限进死信，等人处理。**

```java
int attempt = st.attempt() + 1;
String status = attempt >= MAX_ATTEMPTS ? "DEAD" : "FAILED";
states.put(docId, new IndexState(docId, status, attempt, e.getMessage(), null, 0));
```

实测（`MAX_ATTEMPTS = 3`）：

```
第 1 轮: status=FAILED attempt=1
第 2 轮: status=FAILED attempt=2
第 3 轮: status=DEAD   attempt=3   ← 不再自动重试
再 reindex: {"processed":0,...}     ← DEAD 不在待处理队列里
重新入队: "已重新入队，尝试次数归零"
再 reindex: {"processed":1,...}  → INDEXED/2块
```

四个要素，缺一个就不完整：

| 要素 | 为什么 |
| --- | --- |
| `attempt` 计数 | 区分"偶发失败"和"永远失败" |
| 上限（3–5 次） | 给偶发失败留机会，又不无限重试 |
| `DEAD` 状态 | 把"永远失败"从自动队列里摘出来 |
| 人工重入接口 | 修好文档之后得有办法让它重新跑 |

**别忘了给死信配告警。** 死信队列里躺着的每一条，都是一份"用户问不到的知识"。

## 10.7 检索结果怎么进 prompt

检索到 3 个块之后，别直接拼字符串。四件事要做：

**一、编号，让模型能引用。**

```
[1] 退款政策 · 退款到账时间取决于支付方式：银行卡 1-3 个工作日…
[2] 退款政策 · 定制类商品不参与无理由退款…
[3] 物流时效 · 偏远地区需要在普通时效上再加 2-3 天…
```

要求模型"在答案里用 [1][2] 标注来源"，用户就能点开核对。**这是 RAG 相比微调最大的优势：可溯源。**

**二、带上标题和来源。** 只有正文没有来源，模型不知道这段说的是退款还是物流，容易张冠李戴。

**三、截断要按块，不按总字数。** 平均切每个块的最后一段会得到三个半截的话。要限长就整块丢弃（从最不相关的开始丢）。

**四、最相关的放最前面。** 模型对上下文**中间**的内容利用率最低（这叫"lost in the middle"）。如果按相关度排序后是 1、2、3，直接这个顺序就行；如果你有特殊理由要反过来排，记得把最相关的放开头或结尾，不要放中间。

一个够用的 prompt 骨架：

```
只根据下面的资料回答问题。资料里没有的信息，回答"资料中没有提到"，不要推测。
回答时用 [编号] 标注引用来源。

[1] 《退款政策》 退款到账时间取决于支付方式：…
[2] 《退款政策》 定制类商品不参与无理由退款：…
[3] 《物流时效》 偏远地区需要在普通时效上再加 2-3 天：…

问题：退款一般多久到账？
```

**"资料里没有就说没有"这句话必须写。** 不写的话，模型一定会用常识补全 —— 而常识在业务问题上经常是错的。

## 10.8 结论

一条最小可用的流水线，就这五个状态：

```
PENDING ──处理成功──→ INDEXED
   ↑                    │
   │                    │ 内容/元数据变更
   │                    ↓
   └──人工重入──── DEAD ←──失败 3 次── FAILED
```

四条结论：

1. **增量判据用内容哈希，不用时间戳。** 时间戳在两个方向上都会骗你；哈希只回答"内容变没变"这一个事实。实测只改一篇，就只有一篇的 embedding 被重算。
2. **权限存在块里，就必须把"元数据变更"也当成需要重建。** 漏了这条不是 bug，是越权事故 —— 而且它不报错，只在某天被人发现。
3. **删除必须连带删块，并配一个孤儿块对账。** 检索到一个已删除的文档，是最难查的一类问题。
4. **失败要有终点：计数、上限、死信、人工入口。** 没有终点的失败等于"这篇文档永远不存在"，而且没人知道。
